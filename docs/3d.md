# 3D

O sistema não empacota componente 3D nenhum — isso aqui não é uma API nova,
é o vocabulário que emergiu construindo a sala isométrica da Mothership
Agency (react-three-fiber) em cima dos tokens deste pacote. Registrado
depois da prática, não antes: um capítulo escrito sem um consumidor real
só propagaria suposição.

## Cor de entrada é sempre convertida

Todo material lê a cor computada do CSS (`getComputedStyle`) e converte pra
linear uma vez, num cache — nunca a cada frame:

```ts
function lerToken(nome: string): THREE.Color {
  const valor = getComputedStyle(document.documentElement)
    .getPropertyValue(nome).trim();
  return new THREE.Color().setStyle(valor).convertSRGBToLinear();
}
```

Sem exceção, mesmo tokens que "parecem" já estar prontos. O renderer emite
sRGB com `NoToneMapping`; hex cru sob esse encode clareia tudo — achado
real do consumidor, documentado como erro a não repetir.

## Níveis de superfície

Sem token de "superfície 3D" no sistema — 2D usa `--color-surface`
(vidro), que não faz sentido pra um piso ou uma mesa sólidos. A solução do
consumidor: derivar tudo de `--bg-base`, misturado com branco por uma
fração pequena, crescente conforme a função do objeto — uma escada, não
uma paleta:

| Papel | Fração sobre `--bg-base` |
|---|---|
| Piso base (chão da sala inteira) | 0.016 |
| Piso de zona | 0.018 – 0.045 |
| Mesa | 0.05 |
| Estofado/apoio | 0.07 |
| Detalhe de marca (ex.: marca de "casa" da ilha) | 0.1 |

```ts
function tomDeZona(fator: number, t: TokensCena): THREE.Color {
  return t.bg.clone().lerp(new THREE.Color(1, 1, 1), fator);
}
```

**A mistura acontece em espaço linear, não em sRGB.** Isso é o oposto da
regra de composição 2D (`docs/tokens.md`/`ARCHITECTURE.md` — misturar
`--color-surface` em sRGB e só depois converter): lá é composição de
pixel de tela; aqui é cor de material entrando numa conta de iluminação,
que só é fisicamente correta em espaço linear. É a mesma cautela de "não
inventar valor", aplicada ao espaço de cor certo pra cada contexto — 2D e
3D não compartilham a regra só porque compartilham o token de origem.

O fator de cada nível é leitura de cena (julgamento visual), não um token
novo — não existe "número certo" pra isso além do que lê bem contra a
iluminação da cena.

## Rig de iluminação

Quatro luzes, cada uma com um papel fixo — nenhuma delas sinaliza estado:

```tsx
<ambientLight intensity={0.5} />
<directionalLight position={[20, 40, 18]} intensity={0.6} />
<directionalLight position={[-24, 10, -20]} intensity={0.22} color={accent} />
<pointLight position={[zonaQuente.x, 7, 2]} intensity={0.9} distance={30} color={highlight} />
```

| Luz | Papel | Cor |
|---|---|---|
| `ambientLight` | preenchimento plano, base de visibilidade | sem cor (branco puro do three.js — não é hex literal escrito no código) |
| `directionalLight` principal | "sol" da cena, sombra/volume | idem — luz-chave não carrega marca |
| `directionalLight` secundária | rim frio, intensidade baixa (0.22) | `--color-accent`, mas como **temperatura**, não sinal |
| `pointLight` por zona quente | aquece zonas de permanência (posto do secretário, lounge) | `--color-highlight`, mesma lógica |

A regra que separa as duas últimas do sinal de estado (próxima seção) é a
**intensidade**: um token de marca usado como luz de ambiente fica baixo o
bastante (aqui, ≤0.9, contra os materiais emissivos que valem 1.0 cheio)
pra nunca ser confundido com "isto está no estado X". Cor de marca em
iluminação é mood; cor de marca em material emissivo é dado.

## Material ↔ token

Dois tipos de material, dois papéis:

- **`MeshLambertMaterial`** — qualquer superfície passiva: piso, mobília,
  o corpo de uma figura. Recebe luz da cena, então sua cor lida depende do
  rig acima.
- **`MeshBasicMaterial`** — qualquer coisa que precisa ler como
  autoiluminada, imune à luz da cena: o sinal de estado.

Estado → token é uma função fechada, o par 3D do `tone` de `<Badge>`:

| Estado | Token |
|---|---|
| `ocupado` | `--color-accent` |
| `aguardando_input` | `--color-highlight` |
| `erro` | `--color-danger` |
| `offline` | `--color-gray-900` (mesmo par de cinza do `ocioso`, dois níveis mais escuro — não é cor nova) |
| `ocioso` | `--color-gray` |

O objeto inteiro não vira essa cor — só o elemento de sinal (a "lâmpada")
usa o token cheio, em `MeshBasicMaterial`. O corpo (`MeshLambertMaterial`)
fica na cor neutra de base e só recebe uma mistura leve (~16%, 3% se
`offline`) em direção à cor de estado. O salto de cor forte fica reservado
pro elemento que existe só pra sinalizar — o mesmo "salto único" que já
vale pra 2D (badge vs. texto ao redor), com o material fazendo o trabalho
que em CSS seria peso de fonte ou saturação.

Brilho e ritmo são um eixo **separado** da cor: só `erro` e
`aguardando_input` pulsam (seno, duas frequências diferentes — erro mais
rápido, mais urgente); `ocupado` pulsa bem sutil; `ocioso`/`offline` são
platôs estáticos, cada vez mais escuros. Cor diz qual estado; brilho/ritmo
diz o quão urgente ele é agora — as duas variáveis nunca colapsam numa só.

## A regra irmã dos `--color-on-*`

`--color-on-accent`/`--color-on-danger`/etc. respondem, em 2D: **que cor de
texto garante contraste sobre um fundo de marca saturado?** Em 3D a
pergunta se inverte — não há texto, o "conteúdo" é a própria cor emissiva
— e vira: **que superfície ao redor garante que essa cor emissiva se
distingue?**

A resposta não é um valor de cor, são dois mecanismos:

1. **Teto de valor.** Nenhuma superfície passiva passa de ~10% de mistura
   com branco (tabela de níveis acima) — o material mais claro da cena
   ainda fica bem abaixo do que um `MeshBasicMaterial` a brilho 1.0
   entrega.
2. **Tipo de material, não intensidade de luz.** O sinal ignora a
   iluminação da cena por construção (`MeshBasicMaterial`); todo o resto
   depende dela (`MeshLambertMaterial`). O contraste sobrevive a qualquer
   ajuste do rig de iluminação porque não depende dele — é estrutural, não
   calibrado.

Não existe (ainda) um par de tokens pra isso porque a resposta não é uma
cor: é uma escolha de tipo de material e um teto numérico, os dois vindos
da prática, não de uma medição de contraste como a tabela WCAG que originou
os `--color-on-*` de 2D.
